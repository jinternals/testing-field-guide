01 · Nagle and delayed ACK

Two good ideas that wait for each other

TCP has two old optimisations against tiny packets. The sender holds back a small segment while earlier data is unacknowledged (Nagle). The receiver holds back its ACK, hoping to piggyback it on a reply (delayed ACK). In a request/response exchange where one message goes out in two write() calls, each waits for the other — until a timer fires.

Nagle’s algorithm — the sender

“If there is unacknowledged data (i.e., SND.NXT > SND.UNA), then the sending TCP endpoint buffers all user data (regardless of the PSH bit) until the outstanding data has been acknowledged or until the TCP endpoint can send a full-sized segment.” — RFC 9293 §3.7.4

TCP SHOULD implement it (SHLD-7); there MUST be a way to disable it per connection (MUST-17). In Java that is TCP_NODELAY, off by default on a java.net.Socket.

Delayed ACK — the receiver

“A TCP endpoint SHOULD implement a delayed ACK (SHLD-18) … the delay MUST be less than 0.5 seconds (MUST-40).” An ACK SHOULD go out for at least every second full-sized segment. — RFC 9293 §3.8.6.3

Linux starts each connection in quick-ACK mode and leaves it once the connection looks like request/response (“ping-pong”): a reply sent within the ACK timeout of receiving data counts. From then on, a lone segment waits for the timer.

Measured: 200 requests, 7 ways to send them

Nagle.java — the client side
  static long[] exchange(Socket socket, int writes, int rounds)
      throws Exception {
    OutputStream out = socket.getOutputStream();
    InputStream in = socket.getInputStream();
    long[] rtt = new long[rounds];
    for (int i = 0; i < rounds; i++) {
      long t0 = System.nanoTime();
      write(out, writes);

  • Two writes per message + Nagle = one timer per message. Every round trip took about 41 ms; every fix brought p99 under 0.1 ms.
  • Write each message once. Build it in a buffer (or wrap the stream in a BufferedOutputStream) and flush once: Nagle never has a second small segment to hold.

02 · Connections

Open once, reuse, close carefully

Before the first byte of a request, TCP spends a round trip on the handshake. After the last byte, the side that closes first keeps the connection in TIME_WAIT, holding its port. Both costs are paid per connection — so the number of connections, not requests, is what hurts.

TIME_WAIT

“When a connection is closed actively, it MUST linger in the TIME-WAIT state for a time 2xMSL (Maximum Segment Lifetime) (MUST-13).” “For this specification the MSL is taken to be 2 minutes.” — RFC 9293 §3.6.1, §3.4.2

Sequence numbers stay “busy” until MSL seconds have passed (§3.4.3): the wait keeps old segments from being taken for a new connection’s. Linux does not wait 4 minutes but a fixed 60 s (TCP_TIMEWAIT_LEN). tcp_fin_timeout is something else — how long an orphaned connection may sit in FIN_WAIT_2.

Ephemeral ports run out

A connection is identified by four values: source address and port, destination address and port. To one destination, a client can only vary its own port. The runner’s range is 32768–60999: 28,232 ports. Each closed connection keeps its port for 60 s, so one client address can open at most about 471 new connections per second to one server address and port, for as long as that lasts — unless TIME_WAIT reuse applies.

Reuse is not on everywhere

tcp_tw_reuse lets a new outgoing connection take a port still in TIME_WAIT when that is safe. Its default is 2: loopback traffic only — the runner has 2. So a load test against localhost can open connections endlessly, while the same test against a real host runs out of ports. Test against the network you will run on.

  • Reuse wins even on loopback: a new connection per request cost 4.8× as much — no network latency involved. Over a real network add a round trip per connection, and TLS on top.
  • TIME_WAIT lands on whoever closes first — exactly 2,000 sockets on that side, none on the other. HTTP/1.1 Connection: close from a server leaves them on the server.
  • SO_LINGER(0) left no TIME_WAIT: close() sends a reset instead of a FIN. It also throws away unsent data and tells the peer something went wrong — a tool for errors, not a fix for port exhaustion.
  • A server that never closes left 2,000 sockets in CLOSE_WAIT, and the clients’ ends waited in FIN_WAIT2 — the one state tcp_fin_timeout limits. Growing CLOSE_WAIT in ss means a socket leak in the application.
  • One HttpClient per application. The JDK client keeps idle connections for 30 s (jdk.httpclient.keepalive.timeout) and reuses them. A new client per request means a new connection per request.
  • Load tests: open connections the way production does. A generator that reconnects for every request measures handshakes and can exhaust its own ports; one that never reconnects hides the cost of new users.
  • Watch for it: ss -tan state time-wait | wc -l during a test; connection errors such as “Cannot assign requested address” mean the client ran out of ports.
  • Pools need a limit and an idle timeout shorter than the server’s, or the pool hands out connections the server has already closed.

A timeout bounds one wait, not the call

“The call has a 2-second timeout” is rarely true. Each setting bounds one phase of the call, and the phases nobody set wait forever. Read the JDK’s documentation and source carefully, then measure against servers that misbehave in each phase.

What the request timeout covers

“If the response is not received within the specified timeout then an HttpTimeoutException is thrown … The effect of not setting a timeout is the same as setting an infinite Duration, i.e. block forever.” — HttpRequest.Builder.timeout

04 · Pools and Little’s Law

Throughput, latency and the size of a pool

Every pool is a queue in front of a resource. Little’s Law ties the three numbers you can measure together, for any stable system, whatever the pattern of arrivals: L = λ·W — the average number of requests inside equals the rate they leave times the average time each spends inside.

Three consequences

1. A pool caps throughput: with C connections each busy for S seconds, at most C/S requests per second leave. Our database (4 slots, ~10.2 ms per query as measured) tops out near 394 per second.

2. Past the cap, more callers only add waiting: 64 callers in a system that serves 394/s means W = 64 / 394 ≈ 162 ms each, however the queue is arranged.

3. A bigger pool moves the queue — from the pool into the database, where waiting is more expensive: memory, locks, context switches.

How big, then?

“connections = ((core_count * 2) + effective_spindle_count)” — a starting point from the PostgreSQL project, quoted by HikariCP’s “About Pool Sizing”

The reasoning: a CPU core runs one thread at a time; beyond that, more threads add context switching, not throughput — unless they wait on disk or network. Treat the formula as a first guess, then measure throughput and latency as you change it, as below.

05 · Measuring latency

Coordinated omission: the load test that hides the stall

Most load tests send a request, wait for the answer, then send the next. When the server stalls, the test stalls with it — and stops sending the requests that real users would have kept sending. Those requests are never measured. Gil Tene named this coordinated omission: the tester coordinates with the system it measures, and omits exactly the bad moments.

Two ways to get the truth

Measure from the due time. Keep a schedule — an open workload — and count each request’s latency from when it should have been sent. wrk2 “measures response latency from the time the transmission should have occurred”.

Or correct afterwards. HdrHistogram’s recordValueWithExpectedInterval adds, for a value longer than the expected interval, “an additional series of decreasingly-smaller … value records” — the requests that would have queued behind it.

Open and closed models in load tools

“In a closed model, the execution time of each iteration dictates the number of iterations executed … In the open model, on the other hand, VUs arrive independently of iteration completion.” — k6 documentation

k6: constant-arrival-rate, ramping-arrival-rate (open). Gatling: constantUsersPerSec, rampUsersPerSec (open) versus constantConcurrentUsers (closed). Real users arrive whether or not the last one finished: test with an open model.

The arithmetic of this chapter’s experiment

The program (constants read from CoordinatedOmission.java) sends one request every 2 ms for 10 s — 5,000 due — and the server stalls once, for 1000 ms. Open loop: 500 requests fall due during the stall, 10% of all; they wait from about 1000 ms down to 0, so everything from about p90 up is stall. Closed loop: the client waits with the server, so only one request sees the stall — 1 of 4,501 samples, 0.02%: it can only appear at p99.99 or the maximum. Chapter 5’s second page shows exactly that.

Stop-the-world, or almost never

A garbage collector has to find live objects and make room. Some of that work needs every application thread stopped — a pause. G1, the default on a server-class machine, collects in regions and aims for short pauses, but copies live objects while the application waits. ZGC does that work concurrently, while the application runs, and stops it only briefly.

The collectors, as of JDK 21–24

G1: default when the JVM sees at least 2 CPUs and about 1792 MB (chapter 9). Young and mixed collections copy live objects during pauses; marking of the old generation runs concurrently.

Generational ZGC: JEP 439, JDK 21, enabled with -XX:+UseZGC -XX:+ZGenerational; the default ZGC mode from JDK 23 (JEP 474); the only mode from JDK 24 (JEP 490). Marking and relocation run concurrently; the remaining pauses do not grow with the heap.

Cheap threads, and the one thing that pins them

A virtual thread (JEP 444, final in JDK 21) is a Java thread that is not tied to an OS thread. It runs mounted on a carrier — a platform thread of a small pool — and when it blocks on I/O, a sleep or a lock, it unmounts and the carrier runs another one. Blocking becomes cheap; you can have a thread per task again.

Carriers

The scheduler is a ForkJoinPool whose parallelism is availableProcessors() unless jdk.virtualThreadScheduler.parallelism says otherwise (JDK 21 VirtualThread.java). The runner had 4.

Pinning (JDK 21–23)

Blocking inside synchronized keeps the virtual thread pinned: it cannot unmount, so it holds its carrier while it waits. JEP 491 (JDK 24) lets virtual threads unmount inside synchronized; the jdk.tracePinnedThreads property used here was removed with it.

09 · Containers and CPUs

What the JVM sees inside a container

A container limit is not a smaller machine. It is a cgroup setting: a CPU quota per period, and a memory ceiling. The JVM reads both at start-up (container support has been on by default since JDK 10) and sizes itself from them — the number of CPUs it reports, the heap, the garbage collector, and every thread pool sized from availableProcessors().

CPUs from the quota

--cpus=N writes cpu.max as quota period. HotSpot divides quota by period and rounds up, capped at the host’s CPUs (JDK 21 cgroupUtil_linux.cpp: ceilf(quota / period)). -XX:ActiveProcessorCount overrides the result.

Heap from the memory limit

Without -Xmx, the maximum heap is MaxRAMPercentage of the memory the JVM sees — 25 by default (gc_globals.hpp). MinRAMPercentage (50) is used instead only when memory is so small that half of it is below the default MaxHeapSize (arguments.cpp).

The collector from both

G1 is chosen only on a “server-class machine”: at least 2 active processors and at least 2 GB − 256 MB of memory (os.cpp is_server_class_machine, with an extra check for hyper-threaded packages). Otherwise Serial — one thread, stop-the-world (gcConfig.cpp).

A quota is time, not cores

--cpus=0.5 lets the container run for half of each scheduling period, then stops it until the next one. The JVM still reports 1 CPU and runs one GC thread. A multi-threaded burst can use the whole quota early in the period and then wait — throttling, visible in cpu.stat as nr_throttled and throttled_usec.

10 · The Java Memory Model

What another thread is allowed to see

Without synchronisation, Java promises much less than the source code suggests. The compiler and the CPU may reorder and cache memory accesses as long as a single thread cannot tell. The Java Memory Model (JLS chapter 17) says exactly when another thread is guaranteed to see a write — and that guarantee is the happens-before order.

Data race (JLS §17.4.5)

Two accesses to the same variable conflict if at least one is a write. A program has a data race when two conflicting accesses are not ordered by happens-before.

The guarantee (§17.4.3): “If a program has no data races, then all executions of the program will appear to be sequentially consistent.” With a race, the JMM allows results no interleaving of the source lines can produce.

Happens-before, JLS §17.4.5 (quoted)

  • An unlock on a monitor happens-before every subsequent lock on that monitor.
  • A write to a volatile field happens-before every subsequent read of that field.
  • A call to start() on a thread happens-before any actions in the started thread.
  • All actions in a thread happen-before any other thread successfully returns from a join() on that thread.

Plus program order within a thread, and transitivity. java.util.concurrent documents the same edges for its locks, queues, atomics and futures.

Visibility: a loop that never sees the flag

Happens-before is also about whether a write is seen at all. A thread spinning on a plain field has no happens-before edge with the thread that sets it, so the JIT may read the field once and keep the value. JLS §17.3 says so in nearly these words: “The compiler is free to read the field this.done just once, and reuse the cached value in each execution of the loop.”

StaleFlag.java — the loop runs 1 s, then the flag is set
